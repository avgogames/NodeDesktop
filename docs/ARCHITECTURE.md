# System Monitor: Architecture

A Linux desktop system monitor built with Electron and plain JavaScript,
modelled on [GNOME System Monitor](https://apps.gnome.org/SystemMonitor/).
It has the same three views: **Processes**, **Resources** and
**File Systems**.

This document covers the design of the minimal version on this branch and the
decisions behind it.

---

## 1. Goals and constraints

| Goal | Consequence for the design |
| --- | --- |
| Feature parity with GNOME System Monitor's core | Process list with search, filters, tree view, signals, priority, properties, open files and memory maps; CPU, memory/swap, network and disk graphs; mounted file systems with usage. |
| Low overhead (a monitor must not be what shows up in the monitor) | Read `/proc` directly with async I/O, with no polling shell commands. Sample processes only while that view is visible. Virtualize the process table. |
| Few dependencies | No native addons and no UI framework. The runtime has zero npm dependencies; only Electron and electron-builder are dev dependencies. |
| Secure by default | `contextIsolation`, `sandbox`, no `nodeIntegration`, a strict CSP, a narrow preload API and validation of every IPC argument in main. Privileged actions go through polkit (`pkexec`). |
| Testable | All procfs parsing and list logic are pure functions, tested with `node:test` against fixtures and a fake `/proc` tree. |

Non-goals for the minimal version: other operating systems, per-process GPU
and network usage, configurable columns, and i18n. These are covered in §10.

## 2. High-level architecture

```
┌──────────────────────────── Main process (Node.js) ────────────────────────────┐
│                                                                                 │
│   main.js ── lifecycle, window, single-instance lock, session hardening         │
│      │                                                                          │
│      ├── Settings (userData/settings.json, validated, atomic writes)            │
│      │                                                                          │
│      ├── Sampler ── timer loop, never overlapping, view-aware                   │
│      │     ├── ResourceService   /proc/stat, meminfo, net/dev, diskstats        │
│      │     ├── ProcessService    /proc/<pid>/{stat,statm,io,cmdline}            │
│      │     └── FileSystemService /proc/self/mounts + statfs(2)                  │
│      │              │                                                           │
│      │              └── proc/parsers.js (pure)  proc/reader.js (safe I/O)       │
│      │                                                                          │
│      └── ipc.js ── ipcMain.handle(...) + validation; pushes samples             │
│                                                                                 │
└───────────────▲───────────────────────────────────────┬─────────────────────────┘
                │ invoke (request/response)             │ send (push events)
┌───────────────┴─────── Preload (sandboxed) ───────────▼─────────────────────────┐
│   contextBridge.exposeInMainWorld('monitor', { …typed API… })                   │
└───────────────▲───────────────────────────────────────┬─────────────────────────┘
                │                                       │
┌───────────────┴──────────── Renderer (Chromium) ──────▼─────────────────────────┐
│   app.js ── header bar, view switching, menus, global shortcuts                 │
│     ├── ProcessView ── VirtualTable + processModel (filter/sort/tree)           │
│     ├── ResourcesView ── 4 × LineChart (canvas) + legends                        │
│     └── FileSystemsView ── sortable table with usage bars                       │
└─────────────────────────────────────────────────────────────────────────────────┘
```

**Why sample in main and not in the renderer?** The renderer is sandboxed and
has no filesystem access, which is the point of the sandbox. Main owns all
system access, and the renderer only presents data. This also lets main keep
resource history across a renderer reload, so the graphs are never empty.

**Why not a native module or `systeminformation`?** Everything the app needs
is plain text in procfs. Reading it directly avoids per-tick child processes,
native rebuilds on every Electron upgrade, and a large dependency tree. The
parsers come to about 250 lines and are fully unit-tested.

## 4. Data sources

| Data | Source | Notes |
| --- | --- | --- |
| Process list | `readdir(/proc)` numeric entries | Processes can exit mid-sample; every read tolerates `ENOENT`. |
| Name, state, ppid, nice, threads, CPU ticks, start time | `/proc/<pid>/stat` | `comm` is parsed up to the **last** `)` because names can contain parentheses and spaces. |
| Memory column | `/proc/<pid>/statm` | `(resident − shared) × PAGESIZE`, approximating GNOME's "private" memory. |
| Disk read/write | `/proc/<pid>/io` | Readable only for your own processes unless you are root, so other users' processes show `N/A`. |
| Command line | `/proc/<pid>/cmdline` | Read once per process lifetime and cached. |
| User | owner of `/proc/<pid>` (effective uid) | Cheaper than parsing `status` every tick. Names come from `/etc/passwd`, falling back to an async `getent` lookup. |
| CPU usage | `/proc/stat` | Δbusy / Δtotal per core. Process CPU% = Δ(utime+stime) / Δ(total machine ticks), which is GNOME's default "divide by CPU count" mode. |
| Memory / swap | `/proc/meminfo` | Used = `MemTotal − MemAvailable`, matching GNOME and `free`. |
| Network | `/proc/net/dev` | Sum over interfaces, excluding `lo`, `veth*`, `docker*`, `br-*` and `virbr*`. |
| Disk throughput | `/proc/diskstats` filtered by `/sys/block` | Whole disks only, excluding loop, ram, zram and dm devices, so partitions aren't double-counted. |
| File systems | `/proc/self/mounts` + `fs.statfs()` | Pseudo filesystems are filtered out, squashfs is hidden unless "Show All File Systems" is on, and statfs has a 1.5 s timeout so a dead NFS share can't freeze sampling. |
| Clock ticks / page size | `getconf CLK_TCK`, `getconf PAGESIZE` | Read once at startup, with 100 and 4096 as defaults. |

A recycled pid must never inherit another process's CPU baseline, so all
per-process state is keyed by **`pid:starttime`**.

## 5. Sampling strategy

`Sampler` runs one tick at a time. The next tick is scheduled only after the
current one finishes, so a slow `/proc` read can never pile up overlapping
work.

| Data | When it is sampled |
| --- | --- |
| Resources | Every tick, always, so the graphs have continuous history. Cheap: four files. |
| Processes | Every tick, only while the Processes view is visible and the window isn't minimized or hidden. This is the expensive part, with four reads per pid. |
| File systems | Every 5 s while their view is visible, and immediately on switching to it. |

The interval can be set to 1, 2, 3 or 5 seconds (default 2). History length
scales with it to keep about two minutes of graphs. `refreshNow()` runs an
immediate tick after a view switch or a process action, so killing a process
shows up at once instead of up to one interval later.

## 6. IPC contract

All requests are `ipcRenderer.invoke` → `ipcMain.handle`. Every handler first
checks that the sender is the app's own window, then validates its arguments.

| Channel | Arguments | Validation |
| --- | --- | --- |
| `app:get-initial-state` | none | Returns system info, settings and resource history. |
| `settings:update` | partial settings | Per-key validators; unknown keys and invalid values are dropped. |
| `view:set-active` | view | Must be one of the 3 views. |
| `sampler:refresh` | none | |
| `process:signal` | pid, action, `{elevated}` | Integer pid in range; action ∈ {stop, continue, end, kill}, mapped to the signal in main. |
| `process:renice` | pid, nice, `{elevated}` | Integer nice in −20…19. |
| `process:details` / `process:open-files` / `process:memory-maps` | pid | Integer pid. |

Push events (main → renderer): `sample:processes`, `sample:resources`,
`sample:filesystems` and `sample:error`.

The sandboxed preload cannot `require` local files, so it repeats the channel
names. `test/app.test.js` fails if the two lists ever drift apart.

## 7. Security model

* **Renderer isolation:** `contextIsolation: true`, `sandbox: true`,
  `nodeIntegration: false`. The renderer only sees `window.monitor`, a set of
  functions with fixed channels and no generic `send`.
* **CSP:** `default-src 'none'; script-src 'self'; style-src 'self'`. There are
  no inline scripts or styles. Process-derived strings are inserted with
  `textContent`, or escaped with `escapeHtml` when a dialog builds HTML.
* **Navigation:** `will-navigate` is blocked, `window.open` is denied (https
  links go to the system browser) and all permission requests are denied.
* **Privilege escalation:** the app never runs as root. Signals use
  `process.kill`, and priority changes use `os.setPriority`. On
  `EPERM`/`EACCES` the UI asks the user, then retries via
  `pkexec kill -s SIG pid` or `pkexec renice -n N -p pid`. Both use `execFile`
  with an argument array, so there is no shell and no injection. Polkit owns
  authentication, as with GNOME's `gsm-kill` helper.
* **Settings file:** validated per key on load, so a tampered file can't inject
  odd values. Writes are atomic (temp file + rename).

## 8. UI architecture

### Layout (GNOME HIG)

```
┌ HeaderBar ────────────────────────────────────────────────────────────┐
│ [🔍 Search]          [Processes | Resources | File Systems]   [⏷] [≡] │
├───────────────────────────────────────────────────────────────────────┤
│                         active view                                   │
├───────────────────────────────────────────────────────────────────────┤
│ 213 processes                                          [End Process]  │  (Processes only)
└───────────────────────────────────────────────────────────────────────┘
```

* **View switcher:** a centered stack switcher, also on `Ctrl+1/2/3`.
* **Filter menu (⏷):** All, My or Active Processes, and Show Dependencies
  (tree view).
* **Main menu (≡):** update interval, Show All File Systems, Refresh,
  Keyboard Shortcuts, and About (which shows host, OS, kernel, CPU and memory).
* **Context menu:** Properties, Memory Maps, Open Files, Change Priority
  (presets or a custom nice slider), Stop, Continue, End and Kill. It uses
  GNOME's shortcuts (`Ctrl+S/C/E/K`, `Delete`, `Alt+Enter`, `Ctrl+M/O`).
* **Theme:** Adwaita colors via CSS custom properties. Dark mode follows
  `prefers-color-scheme`, which Electron derives from the GTK theme. Canvas
  charts read the same variables and redraw when the scheme changes.

### Component model

The renderer uses ES modules with plain classes and no framework. State flows
in one direction:

```
main push ──► app.js ──► View.update(data) ──► pure model (buildRows) ──► DOM
user action ──► View method ──► window.monitor.* (invoke) ──► main ──► next push
```

* **`processModel.js`** (pure) holds the filter (all, mine, active, plus the
  search query over name, user, exact pid and command line), the stable sort
  (ties broken by pid so rows don't jitter) and the tree flattening. The tree
  is built with an iterative DFS, so deep process trees can't overflow the
  stack. A child whose parent is filtered out becomes a root, and collapsed
  nodes are tracked by `pid:starttime`.
* **`VirtualTable`** renders only the visible rows plus 6 rows of overscan, at
  a fixed row height. Row elements are recycled from a pool and a cell's text
  is only rewritten when it changes, so 2,000+ processes refresh every second
  without layout thrash. It handles header-click sorting, selection by key
  (which survives re-sorting), arrow, page, Home and End keys, Enter, and
  left/right to collapse or expand tree nodes.
* **`LineChart`** is a canvas chart that is DPR-aware, redraws on resize, and
  coalesces draws with `requestAnimationFrame`. Percentage charts have a fixed
  0–100 axis. Throughput charts auto-scale to readable 1/2/5 × binary-unit
  steps.
* **Dialogs** use the native `<dialog>` element and return promises (confirm,
  priority, tabbed properties with lazily loaded tabs).

## 9. Error handling

| Failure | Behavior |
| --- | --- |
| Process exits mid-sample | Its reads return `null` and it is dropped from that sample. |
| Unreadable files (other users' `io`, `fd`, `maps`) | The value shows as `N/A`, or the tab shows "Permission denied". |
| Signal or renice `EPERM` | The user is offered polkit authentication. `ESRCH` shows a toast. |
| statfs hangs (stale NFS) | Times out after 1.5 s, and the row shows "Unavailable". |
| Sampling throws | Logged in main and shown as a toast, and the loop keeps running. |
| Corrupt settings file | Defaults are used and the file is rewritten on the next change. |

## 10. From minimal to production: next steps

1. **Column chooser and resizable columns**, persisted in settings (GNOME lets
   you show virtual memory, CPU time, started, nice, cgroup, security context
   and more).
2. **Dedicated polkit policy and helper** (`io.github.avgogames…policy`) in the
   deb, instead of generic `pkexec kill`, so the auth dialog names the app.
3. **Per-process network usage** (needs eBPF or netlink, which is privileged).
4. **Smarter memory accounting:** read `smaps_rollup` for PSS on demand.
5. **Worker thread for process sampling** on very large hosts (10k+ pids), to
   keep main's event loop free.
6. **i18n** via message catalogs, and locale-aware number formatting.
7. **Lint and CI:** ESLint, plus a GitHub Actions job that runs `npm test` and
   builds the AppImage and deb.
8. **E2E tests** with Playwright's Electron driver under Xvfb. This was used by
   hand to check this version and should be automated.
